# Code review: Exam Generator, 2026-10-28

**Verdict: Request changes.** There is one High authorization finding: one person can approve every step of the chain. Nothing is Critical. The rest of the code is careful, well documented and well guarded.

- **Branch reviewed:** `phase-10-logs-release` at `2b89d37`, all 10 phases, as the updated `review/REVIEW-TASK.md` on that branch asks. Phases 1 to 6 were also read on `main` at `53aec40`. Where a `main` finding is already fixed on the branch, it is listed under "Fixed on the branch".
- **Prompt:** `review/code-review-prompt.md` (security, reuse, naming, docs, correctness). Our standing Access and kit checks were added on top: the kit copied unchanged, transactions and guarded writes, the error log, data safety.
- **Not done here:** compiling and running. This review ran without Access. The build, the runtime and the error log before and after are covered by the VM visual QA (`qa-2026-10-28.md`) and functional checks (`checks-2026-10-28.md`).
- **Scope:** `access/src` (modules and forms), `access/backend`, `access/build.ps1`. `access/kit` and `access/tools` were checked against the kit's source commit, not reviewed line by line.

## Fixed on the branch (found on `main`, already right on `phase-10-logs-release`)

- `SubmitQuestion` wrote a "Submitted" audit row even when its guarded update matched nothing. It is now in a transaction and checks the row count.
- `SaveQuestion` checked "still a draft or rejected" before its transaction only. It now takes the row with a guarded update inside the transaction, and the same goes for a new version's base.
- `DeleteDraft` relied on the caller's `DeleteProblem`. It now checks again inside the transaction and deletes only a draft.
- Editing a shared reference changed the citation on approved questions with no trace. Reference adds and changes now write audit rows (`ITEM_REFERENCE`).
- `MarkRow`, `ArgLong` and `FieldText` were copied into several forms. They are shared helpers now.
- The first-admin bootstrap ran whenever no admin was active, so it could hand admin to a Personnel admin later. It now runs once, on a new data file, and is recorded (`AdminBootstrapped`).

## Checks with no findings

- **SQL injection:** every text value in SQL goes through `Q()` (quotes doubled) or `LikeLiteral()` (wildcards bracketed). Ids are `Long` parameters, and table and field names in `MoveRow` and `NameProblem` come from code constants only. No user text reaches SQL unquoted.
- **Rights at the write:** every write checks the right in the data file at that moment (`RequireExamAdmin`, `RequireQuestionWriter`, `RequireApprover`, `RequireExamApprover`, `RequireExamMaker`, `RequireReviewer`, `RequireReferenceWriter`), not the TempVars from sign-in. The kit's Personnel switch (`PersonCanUse`) is honoured.
- **Concurrency:** state changes are guarded updates (`StillAtStep`, `ChangeNo` stamps, taking the exam row first in `SignOffTopic`), and anything spanning rows is in a transaction with rollback on error.
- **Error handling:** every event procedure has a `HandleError` handler. Library code passes errors up with `RaiseAgain` context. All `On Error Resume Next` blocks are short and commented. `ERR_NOT_ALLOWED` is shown as a reason, not logged as a fault. `Option Explicit` is in every module and form.
- **Markings:** documents never carry an answer. Each page carries its own highest marking or, when that can't be laid out, the overall one ("never lower than its content"). Unmarked questions block final approval. Documents made before a level reorder are made again.
- **Emails:** plain text, no question text, recipient or reason in them. One email per person, addresses checked, failures logged by person id only.
- **Secrets:** no credentials, keys or connection strings in code. The data file's link password, if any, is read from the link, not stored.

## Done well

- Comments explain why throughout (the transaction ordering in `SignOffTopic`, Jet cache refreshes, the Word section-break layout), and they match the code.
- Rules are checked in one place (`QuestionProblems`, `ReasonProblem`, `RefProblem`, `RecipientProblem`) and reused by the pages.
- Users get concrete, actionable messages for every refusal.

## The three changes that would most improve the code

1. Close the separation-of-duties gap: no person approves two steps of one version, and no editor approves their own edit.
2. Audit every change to roles, admin rights, topic SMEs and the classification order.
3. Back up the data file before a schema upgrade, and don't stamp the new version when part of the upgrade was skipped.
